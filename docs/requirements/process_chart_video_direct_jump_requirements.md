## 0. 本書の位置付け

本書は、個別工程の推移グラフから、該当症例の該当工程開始位置を工程レビュー画面で直接開く機能を定義する。

本書は `docs/requirements/design_ux_update_requirements.md` の分析要件および `docs/requirements/video_review_layout_restoration_requirements.md` の工程レビュー画面要件を補足する。

- 個別工程グラフの点を明示的に活性化した後の選択・遷移仕様は、本書を優先する
- 総手術時間グラフ、前後症例の選択、症例詳細導線、グラフ全体を1つのadjustable controlとする仕様は、既存要件を維持する
- 既存分析要件の「タップ位置から最寄りの症例を選択する」「動画へアクセスしない」は、個別工程点の直接ジャンプ領域が明示的に活性化されるまで維持する。活性化後に限り、選択された1症例の動画状態を読み取り専用で確認できる
- 同一 `videoPath`／動画参照が不変なProvider再通知だけで、利用可能なcontrollerを再生成しない既存要件を維持する。ただし、同一参照のcontroller初期化が失敗し、ユーザーが再確認を明示した場合だけ、§7 R-5および§16.3の逐次再生成を優先する
- データ保全、動画管理、未保存変更の保護、アクセシビリティ、対応端末、画面方向、テーマ、文字倍率等の共通要件は、既存要件を引き続き適用する
- 本機能を理由に最低OS、対応端末、対応方向、オフライン動作またはプライバシー設計を変更しない

本書の「必須」「する」「しない」「維持する」は受け入れ条件である。「推奨」は、不採用の場合に理由と代替策を実装報告へ記載する事項である。

## 2. 背景と目的

白内障執刀ノートでは、症例ごとの総手術時間と個別工程の所要時間を推移グラフで確認できる。

現行の導線は次のとおりである。

```text
グラフ上の位置をタップ
  ↓
最寄りの症例を選択
  ↓
選択カードの「症例詳細を見る」
  ↓
症例詳細画面の「工程記録を開く」
  ↓
工程レビュー画面で対象工程と開始位置を探す
```

本機能の目的は、個別工程の外れ値や変化を発見した直後に、最新の有効な工程開始位置と利用可能な動画がある場合、その症例の同じ工程を動画で確認できるようにすることである。条件を満たさない場合は、§8の安全なフォールバックを使用する。

```text
個別工程グラフの症例点をタップ
  ↓
該当症例の工程レビュー画面
  ↓
該当工程タブを選択
  ↓
該当工程の開始位置を一時停止状態で表示
```

これにより、次の振り返りサイクルを短縮する。

```text
数値の変化を発見する
  ↓
実際の手技を確認する
  ↓
時間変化の理由を考える
  ↓
次の手術へ生かす
```

手術時間短縮等の臨床的効果は本リポジトリだけでは検証できないため、本機能の合否指標には使用しない。

## 3. 用語

### 3.1 症例点

有効な工程所要時間を持ち、個別工程の推移グラフ上で1つの座標を持つ1症例分の論理的な点を指す。

現行のグラフ点は、工程開始位置と工程終了位置がともに存在し、終了位置が開始位置より後である測定だけから生成される。点間隔が狭い場合に視覚マーカーが省略されても、折れ線を構成する症例座標は症例点として残る。ただし、直接ジャンプのタッチ入口になるのは、現在マーカーが描画されている症例点だけとする。選択中の症例点は密度にかかわらずマーカーを表示する。

描画後のデータ変更、症例削除、動画変更および旧不正データに対しては、活性化時とシーク前に症例、対象工程行、工程開始位置および動画を再検証する。工程終了位置はグラフ点を生成する条件だが、動画の開始位置を確認する本機能の遷移・シーク成立条件には再要求しない。復帰時の分析再取得によって、終了位置を失った点はグラフから除外する。

高密度表示で省略された点の論理座標が、選択中等の表示マーカーの直接ジャンプ領域と重なる場合は、44×44の表示マーカー領域を優先する。省略点を選ぶ場合は、その症例の縦帯内かつ全直接ジャンプ領域外（通常は表示マーカーより上または下）をタップする。これにより、表示マーカーの44×44を維持したまま、背景の症例選択と直接ジャンプを曖昧にしない。

### 3.2 点の直接ジャンプ領域

現在マーカーが描画されている各症例点の座標を基準とする、軸平行の44×44 logical pixelsの矩形タップ領域を指す。視覚マーカーが省略されている症例点には、不可視の直接ジャンプ領域を設けない。

- 原則として描画座標を領域の中心とする
- 端の症例では領域全体がplot内へ収まるように平行移動し、軸・ラベル領域へはみ出させない
- 領域の内外は `left <= x < right` かつ `top <= y < bottom` の半開区間で判定する
- 複数の領域が重なる場合は、タップ位置から元の描画座標までの二乗Euclidean距離が最小の点を選ぶ
- 同距離の場合は現在の選択点を優先し、それでも一意でなければグラフ上で新しい側の点を選ぶ
- 各点を独立したSemanticsボタンにはしない
- 点の直接ジャンプ領域内では、背景の線より症例点の活性化を優先する
- 省略点の論理座標または症例別縦帯と表示マーカー領域が重なる場合も、表示マーカー領域内では表示マーカーの活性化を優先する
- すべての直接ジャンプ領域外にあるplot内の線・空白、軸およびラベル領域は、現行どおり最寄り症例の選択だけに使用し、直接ジャンプには使用しない

### 3.3 工程開始位置

動画先頭を0ミリ秒とする `SurgicalStepReview.startMilliseconds` を指す。手術実施日の壁時計時刻ではない。

### 3.4 工程レビュー画面

現行の `StepReviewScreen` を指す。動画プレーヤーだけでなく、工程タブ、開始・終了位置、自己評価、反省点および症例メモを含む編集可能な画面である。

### 3.5 直接ジャンプintent

工程グラフから工程レビュー画面へ渡す、次の2つの安定した識別情報を指す。

- `recordId`
- 対象工程を表す `SurgicalStep.storageId`

表示名、enumの宣言順、グラフ取得時の開始位置または終了位置を、直接ジャンプintentの識別情報として使用しない。

### 3.6 通常導線

症例詳細画面等から、直接ジャンプintentを指定せずに工程レビュー画面を開く既存導線を指す。

## 4. 対象範囲

### 4.1 対象工程

直接ジャンプの対象は、現行コードの `activeIndividualSurgicalSteps` と一致する次の10工程とする。

| 表示名 | `storageId` |
|---|---|
| サイドポート作成 | `side_port_creation` |
| 粘弾性物質注入 | `ovd_injection` |
| CCC | `capsulorhexis` |
| メインポート作成 | `main_port_creation` |
| ハイドロダイセクション | `hydrodissection` |
| 核処理 | `nucleus_removal` |
| I/A | `cortical_irrigation_aspiration` |
| IOL挿入 | `iol_insertion` |
| I/A（粘弾性物質除去） | `ovd_removal_irrigation_aspiration` |
| 創口閉鎖・圧調整 | `wound_closure_and_pressure_adjustment` |

I/AとI/A（粘弾性物質除去）は、表示名の一部が同じでも別工程として扱う。

### 4.2 対象外

次は本機能の対象外とする。

- 総手術時間（`total_surgery_time`）
- 旧データ互換のためだけに保持されている非表示工程
- 未知の工程ID
- 動画クリップの抽出または書き出し
- 工程終了位置での自動停止
- 対象工程の自動ループ
- 工程開始前のプリロール
- グラフからの動画自動再生
- グラフデータまたは動画位置の新規永続化
- 分析・利用状況の外部送信

対象工程の追加・削除は本書へ工程名を重複管理して実装するのではなく、現行コードの有効工程定義を正とする。本書との不一致を発見した場合は、実装前に本書を改訂する。

## 5. グラフ上の操作要件

### G-1. 個別工程の点をタップした場合

ユーザーが個別工程グラフの点の直接ジャンプ領域を1回タップした場合、次を順に行う。

1. 当該点の `recordId` を分析画面の選択症例へ反映する
2. タップ時点の当該点から `recordId` と `step.storageId` を直接ジャンプintentへ固定する
3. 当該 `recordId` と工程を対象に、最新状態を読み取り専用で確認する
4. §8の決定表に従って工程レビュー画面へ直接遷移するか、安全なフォールバックを行う
5. 工程レビュー画面へ遷移する場合は、症例詳細画面を経由しない

確認ダイアログ、遷移先の選択ダイアログまたは追加のモーダル画面を表示しない。

### G-2. グラフ空白をタップした場合

点の直接ジャンプ領域外にあるグラフ領域をタップした場合は、現行どおりタップ位置から最寄りの症例を選択するだけとし、画面遷移しない。

直接遷移は、現在表示されている症例点マーカー周辺の明示的なタップによってのみ開始する。現行のグラフ全高を分割した症例別縦帯を、そのまま直接遷移の入口にはしない。

高密度表示で対象症例のマーカーが省略されている場合は、その症例の縦帯内かつ全直接ジャンプ領域外を最初にタップし、現行どおり最寄りの症例を選択する。選択によってマーカーが表示された後、そのマーカーの直接ジャンプ領域をタップすると直接ジャンプを開始する。省略点の論理座標が別の表示マーカー領域内にある場合、その座標自体のタップは表示マーカーを開くため、省略症例の選択には同じ縦帯の領域外部分を使用する。この場合に限り、任意症例をタッチで開く操作は2回となる。

### G-3. 総手術時間グラフ

総手術時間グラフでは、次の現行仕様を維持する。

- グラフタップは最寄りの症例を選択するだけとする
- 点をタップしても工程レビュー画面を直接開かない
- 前後症例の選択を維持する
- 選択カードの「症例詳細を見る」を維持する

総手術時間の開始位置から動画を開く拡張は、本書の対象外とする。

### G-4. 選択カードと既存詳細導線

個別工程で点を直接開く場合も、分析画面の選択カード、前後症例の選択および「症例詳細を見る」導線を削除しない。

点の直接ジャンプ領域外のタップ、前後ボタン、VoiceOverの増減操作等で症例を選択した場合は、選択カードから引き続き症例詳細を開けること。

個別工程の点をタップする操作自体は、「症例選択だけ」から「選択後に直接ジャンプを開始する」へ意図的に変更する。既存の選択手段を維持することは、点タップの結果を従来と同一に保つことを意味しない。

### G-5. 発見可能性

個別工程グラフには、密度に応じて次と同等の意味を持つ簡潔な案内を表示する。

通常表示：

> 表示されている点をタップすると、その工程の動画を確認します。事前確認で動画または記録位置を利用できない場合は症例詳細を開きます。

マーカーが省略される高密度表示：

> 表示中の点を避けてグラフをタップし症例を選び、表示された点をタップすると工程動画を確認します。

通常表示の「症例詳細を開く」は、遷移前確認で動画または記録位置を利用不能と判定した場合を指す。遷移後の競合、動画長異常、resolver・初期化・シーク失敗では、§8に従って工程レビュー画面に留まる。

総手術時間グラフでは直接ジャンプできると誤認させる案内を表示しない。

### G-6. 連打と多重遷移

点の活性化を受理した時点で遷移可否確認をbusy状態とし、後続の活性化を受け付けない。

- 同じ点の連打でも、異なる点の連続タップでも、最初に受理した1件だけを処理する
- 1回の活性化につき、遷移先routeを最大1件だけ生成する
- busy中は工程指標変更、グラフの点・空白タップ、前後症例、症例詳細、Semanticsの増減・activateおよびpull-to-refreshを無効化し、選択工程と選択症例を変更しない。標準の戻る操作は有効とし、戻った場合は処理を破棄する
- 次の描画フレーム時点でも確認が続いている場合は、busy状態を視覚的に示し、VoiceOverへ1回だけ通知する。次の描画フレームより前にrouteが切り替わる場合は、一瞬だけbusy表示を挟むことを要求しない
- 遷移先routeのpushが受理されて分析画面が非activeになった時点、または分析画面に留まるフォールバック案内を表示した時点でbusy処理を終了する
- `Navigator.push` 相当の戻り値がrouteのpop時に完了するまでの期間を、busy処理として扱わない。分析画面へ戻った時点では再度活性化できる
- 確認失敗時もbusyを解除し、同じ点を再度活性化できる
- 処理中に分析画面が破棄された場合、遅れて画面遷移しない

## 6. 遷移前の確認

### 6.1 確認対象

点の活性化後、タップされた1症例についてのみ次を確認する。

- 症例が現在も存在すること
- 対象工程行が現在も存在すること
- 対象工程の開始位置が `null` ではなく、0以上であること
- 現行の `RecordVideoState` が取得できること

分析画面の初期表示、指標変更、グラフ描画、空白タップによる症例選択、前後症例の選択およびVoiceOverの増減操作では、動画状態を確認しない。

全症例の動画を一括確認しない。動画へのアクセスは、個別工程点が明示的に活性化された後、選択された1症例に限定する。

症例と対象工程の存在、および開始位置が `null` でなく0以上であることを先に確認する。ここでフォールバックが確定した場合は、不要な動画状態確認を開始しない。

### 6.2 読み取り専用

遷移可否の確認は読み取り専用とし、次を行わない。

- 欠落した工程行の作成
- 症例または工程記録の更新
- 工程時刻の補正または永続化
- 動画参照の変更

欠落行を作成する `ensureStepReview` 相当の処理を、遷移可否判定に使用しない。

利用可能な旧外部動画を工程レビュー画面で解決する際に、既存仕様によるbest-effort移行が行われることは妨げない。

### 6.3 動画状態

現行の動画状態を次のとおり扱う。

| `RecordVideoStateKind` | 遷移前の判定 |
|---|---|
| `availableManaged` | 直接ジャンプ可能 |
| `availableLegacy` | 直接ジャンプ可能。遷移先で既存の解決・移行処理を使用する |
| `unregistered` | 直接ジャンプ不可 |
| `missing` | 直接ジャンプ不可 |
| `invalidReference` | 直接ジャンプ不可 |
| `checkFailed` | 直接ジャンプ不可。動画実体なしとは断定しない |

動画登録・差し替え前の検査を指すpreflightを、保存済み動画の直接ジャンプ可否を表す用語として使用しない。ただし、`availableLegacy` の既存best-effort移行では、コピー前の既存preflightが実行され得る。本機能はその安全確認を迂回しない。

`checkFailed` は、動画状態確認が正常に完了して返した分類値である。動画状態を返すFuture自体が例外終了した場合とは区別し、後者は§8の「動画状態確認処理そのものの失敗」として扱う。

本版では、利用不能状態を症例詳細へ確実にフォールバックすることを、動画状態確認を省略した最速遷移より優先する。このため、活性化後に選択症例の状態を事前確認し、直接遷移先でもrace対策として再検証する二段階の読み取りを許容する。1回目の結果を使い回して遷移先の現在性確認を省略しない。

## 7. 工程レビュー画面の初期表示

### R-1. 対象工程タブ

直接ジャンプintentを伴って工程レビュー画面を開いた場合、対象工程タブを必ず初期選択し、スクロール可能なタブバー内で見える位置に表示する。

基準コードではタブcontrollerを総手術時間のindex 0で初期化し、レビュー初回同期後、総手術時間より後に最初の未完了工程があり、まだindex 0ならその工程へ移動する。直接ジャンプintentによる対象工程選択は、この既存のpost-frame選択より優先され、後から上書きされない。

通常導線では、直接ジャンプ用のタブ選択と初期シークを発火させず、上記の既存タブ選択を維持する。

### R-2. 初期シークの成立条件

次をすべて満たした場合だけ、対象工程開始位置への初期シークを実行する。

- 対象症例と対象工程の最新永続化データを取得済みである
- 対象症例と対象工程行が現在も存在する
- 工程レビュー画面のdraft初期同期が完了し、対象工程の最新記録を表示できる
- 対象工程の開始位置が `null` ではない
- 動画プレーヤーの初期化が正常に完了している
- 動画の長さが取得でき、0ミリ秒より大きい
- `0 <= startMilliseconds < videoDurationMilliseconds` を満たす
- 初期化した動画参照が、症例の最新 `videoPath` と一致する
- 画面が現在も有効で、当該routeがcurrentであり、対象controllerが破棄または置換されていない
- 当該直接ジャンプintentの初期シークをまだ実行していない

グラフ描画時に取得した開始位置を、そのまま初期シークへ使用しない。遷移先で対象症例・対象工程をfresh readし、保存済み動画参照を取得した後、動画解決またはcontroller初期化を始める前に、`recordId`、`storageId`、`startMilliseconds` および `videoPath` の候補snapshotを作る。

動画controllerへ初期シーク要求を渡す直前に、対象症例と対象工程行が存在し、候補snapshotの `recordId`、`storageId`、開始位置および動画参照が現在値と一致することを確認する。§7 R-5で定める同一動画のlegacy移行例外を除き、一致しない場合は自動シークを中止してintentを破棄し、変更されたことを案内する。新しい値を追跡して自動シークを再試行しない。一致する場合だけ候補snapshotの開始位置を渡し、要求後の変更による自動再シークも行わない。

`mounted == true` でも、確認dialog、動画ヘルプまたは別routeが前面にある間は当該工程レビューrouteをcurrentとみなさない。fresh read、動画resolver、controller初期化、動画長取得、直接ジャンプ準備中またはシーク完了待ちのcontroller error、およびシークの各非同期結果は、UIまたはintent状態へ適用する直前にrouteのcurrent性を再確認する。pending、retry中またはシーク要求待機中に非currentとなった場合は、古い結果、エラー、成功通知および追加シークを前面routeへ反映せず、直接ジャンプを終了する。直接ジャンプ処理が安定終端した後の通常再生runtime errorは、本要件によるroute guardの対象を外れ、既存の動画回復要件に従う。

すべての非同期処理が既に完了した安定したretryable状態で、ユーザーが既存の動画ヘルプを開いただけの場合は、明示的な再確認権を保持してよい。この例外中も非current routeへ新しい結果を適用せず、戻った後のユーザー操作によってのみ再試行する。

### R-3. 準備中の表示

対象工程データと動画の準備が完了し、初期シークの成否が確定するまで、次と同等の意味を持つ準備中状態を表示する。

> CCCを開いています…

- 工程名は実際の対象工程名とする
- 未確定の暫定0秒位置をジャンプ成功状態として一瞬表示しない。ただし、永続化された有効な `startMilliseconds == 0` は正常な開始位置として扱う
- 初期シークと競合する再生、スキップ、Slider操作等の位置依存操作を有効にしない
- 準備中でも戻る操作を妨げない

### R-4. シーク位置

正常時は、動画先頭を0ミリ秒とする対象工程の `startMilliseconds` を、そのままシーク要求へ使用する。

```text
CCC開始位置 = 222500 ms
初期シーク要求 = 00:03:42.500
```

アプリ層の自動テストでは、controllerへ渡すシーク要求が保存済み開始位置と同じミリ秒値であることを合否とする。対応するiOS／iPadOS上では固定動画fixtureを使い、成功表示後にnative playerから取得した現在位置が開始位置から±100ミリ秒以内であることをintegration試験で確認する。さらに400ミリ秒の実時間経過後にnative位置を再取得し、最初の取得位置との差および開始位置との差がともに±100ミリ秒以内で、一時停止状態が維持されていることを確認する。

±100ミリ秒を超える差を「キーフレーム差」として無条件に合格させない。特定の対応形式で基準を満たせない場合は、形式、端末、OS、要求位置、報告位置および差を記録し、補正方針をユーザー判断事項として報告する。アプリ側で別工程、終了位置またはグラフ取得時の古い開始位置へ置き換えてはならない。

### R-5. 一回限りの適用

初期シークは、1つの直接ジャンプintentにつき最大1回とする。

- Widgetの再buildだけでは再実行しない
- Providerの通常再通知だけでは再実行しない
- lifecycle復帰だけでは再実行しない
- ユーザーが再生位置を変更した後に、初期位置へ巻き戻さない
- シーク要求を発行した時点で、後続の成功または失敗にかかわらず当該intentを消費済みとする

intentの状態を次のとおり扱う。`consumed` と `abandoned` は終端状態、`pending` は処理中、`retryable` はユーザーの明示操作によってだけ `pending` へ戻せる待機状態とする。

| 状態 | 条件とその後の挙動 |
|---|---|
| pending | 初期シーク要求前で、同じ症例・工程・候補snapshotの開始位置・動画参照について準備中 |
| consumed | 初期シーク要求を1回発行済み。成功・失敗、その後のデータ変更または症例削除にかかわらず自動再シークしない |
| abandoned | 初期シーク要求前の症例・工程位置の消失、範囲外位置、別動画への変更、画面破棄等で自動シークを中止。Provider再通知やlifecycle復帰で再開しない |
| retryable | 同じ候補snapshotの開始位置および動画参照について、動画解決または初期化だけが失敗し、まだシーク要求を発行していない状態。ユーザーが既存の再確認を明示的に実行した場合だけpendingへ戻せる |

同じ動画の明示的な再確認が行われた場合は、retryableであり、まだシーク要求を実行しておらず、症例、工程、候補snapshotの開始位置および動画参照が変わっていない場合に限り、準備を再開する。

遷移前確認で直接ジャンプ不可または確認処理失敗が確定し、症例詳細へフォールバックするか分析画面に留まる場合は、受理中のintentをabandonedとして終了する。再試行は、同じ点の新しい活性化から新しいintentとして開始する。

初期シーク要求前に、ユーザー操作または外部更新により動画が再登録、差し替え、削除もしくは別動画へ変更された場合、または工程位置が変更・消去された場合は、古い直接ジャンプintentをabandonedとする。初期シーク要求後に動画変更または症例削除が発生した場合は、intentをconsumedのまま維持し、古いcontrollerと遅延完了を無効化して追加の自動シークを行わない。要求後に工程位置だけが変更された場合は、利用可能なcontrollerを維持し、intentをconsumedのまま、要求の置換と追加の自動シークを行わない。

`availableLegacy` の既存best-effort移行によって同一動画が管理領域へコピーされ、参照が旧絶対パスから管理パスへ正規化された場合は、intentを破棄しない。この場合に限り、同一動画であることを確認して候補snapshotの `videoPath` を移行後の管理参照へ1回だけ結び直し、最新参照のcontrollerで同一intentの初期シークを最大1回だけ実行する。移行に失敗して既存の外部原本を使用する場合も、外部原本と候補snapshotの参照の対応を確認する。

### R-6. 再生状態と表示

- 初期シーク完了後も動画を一時停止状態に保つ
- 自動再生しない
- 対象工程タブと現在の動画位置を同時に確認できる
- VoiceOverでは「CCCの開始位置へ移動しました」等、工程名と完了を1回だけ通知する
- 動画の継続的な位置更新ごとに完了通知を繰り返さない
- タブ選択または初期シークだけで、工程記録をdirtyにしたり保存したりしない

### R-7. 初期シーク失敗

シーク要求が失敗した場合は、対象工程タブに留まり、次と同等の非破壊案内を表示する。

> CCCの開始位置へ移動できませんでした。シークバーまたは記録済み開始位置から確認してください。

- 未処理例外にしない
- 成功通知を表示しない
- 工程時刻、評価、反省点、症例メモまたは動画参照を変更しない
- 利用可能な既存の手動再生・シーク・再確認操作を維持する

### R-8. 範囲外位置

開始位置が負値、動画末尾以後、動画長が0以下または動画長を取得不能な場合は、正常な直接ジャンプとして扱わない。

遷移前確認で負値を検出した場合は§8の症例詳細フォールバックを使用する。本節は、遷移後の再取得で値が負値へ変わった場合や、防御的に直接ジャンプintentを処理する場合にも適用する。

- 範囲外の開始位置を動画controllerの初期シークへ渡さない
- 安全機構として低層でクランプしても、その位置を直接ジャンプ成功として表示しない
- 対象工程タブに留まり、「記録位置が動画の範囲外のため自動で移動できませんでした」と同等の案内を表示する
- 既存データを自動補正または自動保存しない
- 初回fresh readの時点で開始位置が `null` または負値なら、不要な動画アクセスを避けるため直接ジャンプ用resolverとcontrollerを自動起動しない
- 既存の「動画を再確認」を維持し、ユーザーが明示した場合だけ通常の動画解決を開始する。利用可能ならcontrollerと手動操作を復旧するが、古い直接ジャンプintentを再開せず自動シークしない
- 上記の明示的な復旧後も、手動操作と既存の工程位置再設定導線を維持する

## 8. フォールバックと競合時の決定表

遷移前確認と遷移後の非同期処理では、次の挙動を必須とする。

| 状態 | 必須挙動 |
|---|---|
| 症例、工程開始位置、動画が利用可能 | 症例詳細を経由せず工程レビュー画面を開き、§7に従う |
| 症例が削除済み | 新しい画面を開かず分析データを再取得し、「症例が見つかりませんでした」と非モーダルに案内する |
| 症例または工程の確認処理に失敗 | 新しい画面を開かずbusyを解除し、「症例を確認できませんでした。もう一度お試しください」と再試行可能に案内する |
| 動画状態確認処理そのものが例外終了 | 新しい画面を開かずbusyを解除し、「動画の状態を確認できませんでした。もう一度お試しください」と案内する。`checkFailed` や動画実体なしとは断定しない |
| 工程行がない、開始位置が `null` または負値 | 症例詳細画面へフォールバックし、「この工程の記録位置を取得できませんでした」と案内する。controllerと初期シークを生成しない |
| `unregistered` | 症例詳細画面へフォールバックし、「この症例には動画が登録されていません」と案内する。既存の動画登録導線を使用する |
| `missing` | 症例詳細画面へフォールバックし、動画実体なしの既存表示と再登録・差し替え導線を使用する。初期シークしない |
| `invalidReference` | 症例詳細画面へフォールバックし、不正参照の既存表示と回復導線を使用する。参照を開かず初期シークしない |
| `checkFailed` | 症例詳細画面へフォールバックし、実体なしと断定せず、既存の再確認導線を表示する。初期シークしない |
| `availableManaged` | 工程レビュー画面へ直接遷移し、最新参照との一致を再確認して§7の成立条件を満たす場合だけ初期シークする |
| `availableLegacy` | 工程レビュー画面へ直接遷移し、既存のbest-effort移行と外部原本利用方針を維持した上で、§7の成立条件を満たす場合だけ初期シークする |
| 利用可能判定後かつ初期シーク要求前に動画が削除・別動画へ変更された | 別画面へ自動で戻さず工程レビュー画面に留まり、既存の動画エラー・再確認・再登録UIを表示する。古いcontrollerへシークせずintentをabandonedとする |
| 初期シーク要求後に動画が削除・別動画へ変更された | intentをconsumedのまま維持し、旧controllerを論理的に無効化して遅延完了を破棄する。追加の自動シークを行わず、工程レビュー画面で既存の動画エラー・再確認・再登録UIを表示する |
| `availableLegacy` の解決中に同一動画が管理領域へ移行された | 旧参照に結び付くcontrollerと完了結果だけを破棄し、intentはpendingのまま維持する。同一動画の確認後、候補snapshotとcontrollerを移行後参照へ1回だけ結び直して初期シークを最大1回実行する |
| 直接遷移後かつ初期シーク要求前に症例が削除された | 自動シークせずintentをabandonedとし、controllerを論理的に無効化する。draft未初期化なら既存の「症例が見つかりません」状態と再読み込み・戻る導線を、初期化済みなら既存の削除bannerとdraftのコピー・破棄・戻る導線を表示し、「症例が削除されたため工程動画を開けませんでした」と1回だけ案内する |
| 初期シーク要求後に症例が削除された | intentをconsumedのまま維持し、旧controllerを論理的に無効化して遅延完了を破棄する。初期化済みdraftを消去せず、既存の削除bannerとdraftのコピー・破棄・戻る導線を表示し、追加の自動シークを行わない |
| 初期シーク要求前に開始位置が候補snapshotから変更・消去された、または対象工程行が消失した | 工程レビュー画面に留まり、自動シークせずintentをabandonedとする。最新状態を表示し、有効な別位置がある場合は「工程位置が更新されました。記録済み開始位置から確認してください」、位置がない場合は「工程の記録位置が削除されたため自動で移動できませんでした」と案内する |
| 初期シーク要求後に開始位置が変更・消去された、または対象工程行が消失した | intentをconsumedのまま維持し、実行中の要求を別位置への自動シークへ置き換えず、追加シークもしない。最新の工程記録を表示し、有効な別位置がある場合は更新を、位置がない場合は削除を上記と同等に案内する |
| 遷移後の動画解決または動画初期化に失敗 | 工程レビュー画面に留まり、既存の再生失敗・再確認・動画選択UIを表示する。シーク要求前かつ候補snapshotの開始位置・動画参照が不変ならintentをretryableとする |
| 動画長が0以下、取得不能、または開始位置が動画末尾以後 | §7 R-8に従い、自動シークせず範囲外を案内し、intentをabandonedとする |
| `seekTo` 相当の処理が失敗 | §7 R-7に従い、intentをconsumedとし、対象工程タブと既存データを保持して手動の回復操作を提供する |
| 初期シーク要求前に画面を閉じた | intentをabandonedとし、遅延完了を破棄してシーク、`setState`、追加遷移または通知を行わない |
| 初期シーク要求後に画面を閉じた | intentをconsumedのまま維持し、遅延完了を破棄して追加シーク、`setState`、追加遷移または通知を行わない |

フォールバックで症例詳細画面を開く場合も、同一Navigatorへpushし、分析画面を置換しない。

症例詳細へフォールバックする各状態では、遷移先がactiveになった後、その画面上で理由を1回だけ非モーダルに表示し、VoiceOverへ通知する。工程位置の欠落は専用のAppSnackBarまたはインラインbannerで案内する。動画4状態は同じ方法で理由を通知した上で、症例詳細の既存状態カードと回復操作を正として使用する。push前の分析画面だけにSnackBarを出して、遷移後に理由が見えなくなる実装は不可とする。

## 9. 非同期処理と状態競合

### 9.1 現在性の確認

非同期処理の各結果は、適用直前に少なくとも次が一致する場合だけ使用する。

- 受理した `recordId`
- 対象工程の `storageId`
- 現在の直接ジャンプintent
- 現在の動画参照
- 現在のcontroller世代または同等の識別子
- 現在表示中のroute

routeについてはStateの `mounted` だけでは成立としない。直接ジャンプがpending、retry処理中、またはシーク完了待ちのconsumedである間は、結果の適用、エラー表示、intentの状態遷移、controller生成およびシーク要求の各境界で、当該routeがcurrentであることを確認する。

resolverが返した動画ファイルをcontrollerへ結び付ける直前に、repositoryから症例を再読込し、その時点の永続化済み `videoPath` と解決結果の参照対応を確認する。Providerの通知順またはresolver内部で得た古いrecordだけを根拠に適用しない。

動画参照metadataを返さない既存互換APIが `File` だけを返す場合も、返却直前に最新症例を再読込する。通常解決またはlegacy移行失敗では入力参照、legacy移行成功では正規化済み管理参照と最新 `videoPath` が一致する場合だけ `File` を返し、症例削除、再読込失敗または別参照への差し替え時は `null` へfail-closedする。古い呼出しの中で最新の別参照を自動解決し直し、意図しない追加legacy移行を起こさない。

候補snapshot作成後に動画参照A→C→A、または工程開始位置X→Y→XのようなABA変更を一度でも観測した場合は、最終値が候補と再一致しても古いintentを復活させない。`availableLegacy` の同一動画正規化だけは、resolverが明示した旧参照Aと正規化済み管理参照Bの組だけを許可する。処理中に第三の参照Cを観測した場合は、その後AまたはBへ戻っても正規化例外を適用しない。

### 9.2 古い完了結果

次の古い完了結果は破棄する。

- 症例Aを閉じて症例Bを開いた後に完了した症例Aの処理
- controllerのdisposeまたは置換後に完了した初期化・シーク
- 動画参照の変更後に完了した旧参照の解決・初期化
- 候補snapshot作成後、初期シーク要求を渡す前に対象工程の開始位置が変更された場合の古い開始位置
- 分析画面または工程レビュー画面の破棄後に完了した処理

古い完了結果により、別症例のcontroller、再生位置、タブ、busy状態またはエラー表示を変更しない。

同一動画のlegacy移行では旧参照に結び付く完了結果だけを破棄し、直接ジャンプintentは維持する。初期シーク要求前のそれ以外の動画参照変更、および候補snapshot作成後の工程開始位置変更ではintentをabandonedとし、新しい値を追跡して自動シークしない。初期シーク要求後の変更ではintentをconsumedのまま維持し、旧要求を置換せず追加の自動シークを行わない。

非current routeで完了した初期化、動画長取得不能、直接ジャンプ準備中またはシーク完了待ちのcontroller error、およびシーク結果は、予約済みのroute非current処理と完了順が同一フレーム内で逆転しても適用しない。完了側自身がcurrent性を確認し、予約済みcallbackだけへ排他制御を依存させない。直接ジャンプが安定終端した後の通常再生runtime errorは、既存の動画回復UIへ反映してよい。

### 9.3 資源管理

- 同時に有効な動画controllerを1件以下とする
- 直接ジャンプで生成したcontrollerは、画面破棄または置換時に直ちにwidgetから論理的に切り離し、世代を無効化する。`ValueListenableBuilder` 等のlistenerが外れる次の描画フレームを明示的に要求し、そのフレームで物理disposeを開始して完了・失敗を処理する。dispose開始まで旧controllerを再参照せず、遅延または失敗を未処理例外にせず、古いcallbackから画面を更新しない
- 初期シーク後の動画位置通知で、追加の初期シークを発生させない。画面全体を動画位置通知ごとに再buildしない既存共通要件も維持する

## 10. 戻る操作と分析画面の更新

### 10.1 clean状態

工程レビュー画面に未保存変更と保存処理がない場合、標準の戻る操作1回で元の分析画面へ戻る。

同一Navigatorへのpush遷移を用い、次を可能な限りではなく必須として保持する。

- 表示していた工程指標
- 直接ジャンプした症例の選択
- 分析画面の縦スクロールoffset。ただし再取得後の最大scroll extentを超える場合は有効範囲へクランプする
- 選択点と選択カード。再取得後に対象点が消えた場合は§10.3のフォールバックを使用する

VoiceOverを使用中で同じ工程のグラフが残る場合は、そのグラフのadjustable controlへフォーカスを戻す。対象点が消えてもグラフが残る場合は同じcontrolの新しい選択点へ、グラフが空状態になった場合は当該工程の空状態見出しへフォーカスを戻す。

### 10.2 dirty状態と保存中

工程レビュー画面は編集可能なため、既存の未保存変更保護を迂回しない。

- dirty状態では、既存の保存・破棄・キャンセル確認を維持する
- 保存中は既存仕様どおり離脱させない
- 「戻る1回」はcleanかつ保存中でない場合に限る

### 10.3 復帰時の再取得

工程レビュー画面またはフォールバック先の症例詳細画面から分析画面へ戻るたびに、分析データを再取得する。

- 工程時刻が変更された場合は、グラフ、平均および選択カードへ反映する
- 対象点が引き続き有効な場合は、同じ `recordId` の選択を維持する
- 工程時刻変更等で対象点が消えた場合は、その工程の最新有効点を選択する
- 対象工程に有効点が0件になった場合は、既存の空状態を表示する
- 症例が削除された場合は、削除済み症例の選択を解除し、上記規則へフォールバックする
- 再取得に失敗した場合は、既存の分析エラー表示と再試行導線を使用する。選択工程と選択症例のstateは失わず、再試行成功後に本節の選択・scrollフォールバックを適用する

## 11. アクセシビリティ

### 11.1 グラフのSemantics

グラフは現行どおり全体を1つのadjustable Semanticsコントロールとし、密集する各点を独立したSemanticsボタンにしない。

個別工程グラフでは、操作を次のとおり分離する。

| 操作 | 結果 |
|---|---|
| increment | 次の新しい症例を選択する。遷移しない |
| decrement | 次の古い症例を選択する。遷移しない |
| activate / tap | 選択中症例の対象工程について、§6以降の直接ジャンプ処理を開始する |

読み上げには、全件数中の位置、日付、左右眼、工程名および所要時間を維持する。個別工程では次と同等のhintを追加する。

> 上下スワイプで症例を選択し、ダブルタップでこの工程の動画を開きます。

総手術時間では直接ジャンプ用のactivate actionまたはhintを追加しない。

### 11.2 支援操作

VoiceOverだけで、次を完了できること。

1. 個別工程を選ぶ
2. 対象症例を選ぶ
3. 直接ジャンプを活性化する
4. 対象工程タブと開始位置を確認する
5. 元の分析グラフへ戻る

### 11.3 レイアウトと読み上げ

- 文字倍率2.0でも、案内、busy表示、対象工程タブ、エラー、回復操作および戻る操作へ到達できる
- iPhone、iPad、宣言済み方向、iPad Split Viewおよび動的リサイズでoverflowまたは操作喪失を発生させない
- `MediaQuery.disableAnimations == true` では、本機能が追加する非必須モーションを停止する
- busy状態、成功、失敗を色だけで表現しない
- 成功・失敗の通知を重複読み上げしない

## 12. データ・プライバシー・性能

### 12.1 データモデル

本機能のためだけにDB schemaを変更せず、次の既存データを利用する。

- `SurgeryRecord.id`
- `SurgeryRecord.videoPath`
- `SurgicalStep.storageId`
- `SurgicalStepReview.startMilliseconds`
- 現行の動画状態と動画解決処理

グラフ側に工程開始位置または動画状態を別途永続化しない。

### 12.2 データ保全

次を禁止する。

- 直接ジャンプ、失敗またはフォールバックを理由とする工程時刻の変更・消去
- 範囲外位置の自動補正・保存
- 動画エラーを理由とする評価、反省点または症例メモの消去
- 読み取り処理による欠落工程行の暗黙作成

`availableLegacy` を工程レビュー画面で開いた際に、既存仕様のbest-effort移行が管理領域へ動画をコピーし、`videoPath`、`videoDisplayName` および `updatedAt` を更新することは、この禁止事項に含めない。工程時刻、評価、反省点および症例メモは変更せず、外部原本を削除せず、既存の移行失敗時フォールバックを維持する。

工程レビュー画面の既存互換処理が、欠落している工程の空行を `surgicalStepsInDisplayOrder` に従って補完することも、この禁止事項に含めない。ただし、遷移前確認では補完せず、フォールバックだけで工程行を作成せず、開始・終了位置を自動入力しない。

### 12.3 プライバシーとオフライン動作

- 既存のローカル専用・オフライン動作を維持する
- 症例、工程時刻、動画または操作履歴を外部送信しない
- 既存の保護ストレージ、旧外部動画およびバックアップ除外方針を変更しない

### 12.4 性能

- 分析画面の表示、指標変更または症例選択だけでは、動画resolverまたは動画controllerを起動しない
- 明示的に活性化された1症例だけの動画状態を確認する
- 1件、2件、50件のグラフで正しい症例を特定できる
- 制御可能な遅延resolverの完了待ちでも、次の描画フレームでbusyを表示でき、標準の戻る操作に応答する
- 工程レビュー画面のopen／backを繰り返しても、離脱時点で論理的に有効なcontrollerまたは利用可能な古いcallbackを残さず、同時に論理的に有効なcontrollerが1件を超えない。旧物理controllerはlistener解除のため最大1描画フレームだけ残ってよいが、次フレームでdisposeを開始する。明示的な再確認または動画変更による逐次的なcontroller再生成は許容する
- 動画位置通知、再build、Provider再通知またはlifecycle復帰により、初期シーク要求を追加発行しない

## 14. テスト要件

### 14.1 正常系

1. 対象点の直接ジャンプ領域を1回タップする

3. 症例詳細画面を経由せず、工程レビュー画面が1画面だけ開く

### 14.2 取り違え防止

- 複数症例の同一工程から、それぞれ正しい症例動画を開く
- 同一症例のCCCとI/Aから、それぞれ異なる正しい位置を開く

### 14.3 グラフ操作

- 個別工程の点の直接ジャンプ領域は直接遷移する
- 個別工程のグラフ空白は症例選択だけを行い、遷移しない
- 直接ジャンプ領域が軸平行の44×44であり、plot端では大きさを保ったまま内側へ移動する
- 領域のleft／top境界上は領域内、right／bottom境界上は領域外として、§3.2の半開区間どおりに判定する
- 複数領域の重なりでは二乗Euclidean距離、現在の選択点、新しい側の順で優先する
- 点の直接ジャンプ領域と背景線が重なる場合は点を開き、軸・ラベル上および全直接ジャンプ領域外ではrouteを生成せず最寄り症例の選択だけを行う

- 50件等の高密度表示では、マーカーが省略された症例の縦帯内かつ全直接ジャンプ領域外の1回目のタップは症例選択だけを行い、選択マーカーを表示する。そのマーカーの2回目のタップで同じ `recordId` を開く。省略点の論理座標が別の表示マーカー領域内に重なるfixtureでは、重なり座標が表示点を開き、同じ省略症例の縦帯にある領域外タップが省略症例を選ぶことを確認する
- 通常表示と高密度表示で§5 G-5の異なる案内を表示し、総手術時間では直接ジャンプ案内を表示しない
- 総手術時間の点または空白タップは選択だけを行い、直接遷移しない
- 前後症例と「症例詳細を見る」を維持する

### 14.4 動画状態とエラー

次をそれぞれ独立して確認する。

- `unregistered`
- `availableManaged`
- `availableLegacy`
- `missing`
- `invalidReference`
- `checkFailed`
- 動画状態確認Future自体の例外終了
- 遷移前に症例が削除された場合
- 遷移前に対象工程行が存在しない場合
- 症例または工程のfresh readが例外終了した場合
- 遷移後の動画解決Future自体の例外終了
- 動画初期化失敗
- 初期シーク失敗
- 動画長0
- 動画長取得不能
- 開始位置 `null`
- 開始位置が負値
- 開始位置0
- 開始位置と動画長が同値
- 開始位置が動画長を超える
- SQLite signed 64-bitの最小値と最大値、および `start = INT64_MAX - 1`、`end = INT64_MAX` の境界値

各状態で、§8に定義した画面、案内、回復操作、controller生成有無およびシーク有無と一致することを確認する。「クラッシュしない」だけでは合格としない。

症例詳細への各フォールバックでは、遷移先がactiveになってから理由を1回だけ表示・読み上げ、既存の状態カードと回復操作へ到達できることを確認する。分析画面に留まる失敗では、busy解除後に案内と再試行ができることを確認する。

境界値は `Duration` 生成前に整数として検証し、範囲外値をcontrollerへ渡さない。開始位置 `null` と `unregistered` が同時に存在する複合ケースでは、工程位置の確認結果を優先し、動画状態確認を呼び出さない。同様に、症例または工程がない場合も動画状態確認を呼び出さない。

開始位置 `null` または負値を遷移先で防御的に処理するfixtureでは、初期表示時の動画resolver・controller・自動シークがすべて0件であることに加え、ユーザーが「動画を再確認」を明示した後だけ通常controllerが生成され、手動操作を復旧し、自動シークは0件のままであることを確認する。

`availableLegacy` は、移行成功時に動画関連metadataだけが更新され外部原本が残ることと、移行失敗時に外部原本から再生・シークできることを別々に確認する。

### 14.5 非同期・競合

制御可能なFutureまたは同等のテスト手段で、次を確認する。

- 症例・工程のfresh readが完了するまではdraft同期、動画resolver、controller生成および初期シーク要求が0回である。fresh read完了後は、draft初期同期→動画初期化と動画初期化→draft初期同期の両順序を制御し、両方が揃う前は初期シーク要求0回、揃った後だけ最大1回である
- 同一点を連打する
- 症例Aの処理中に症例Bをタップする
- busy中に工程指標、前後症例、空白タップ、症例詳細、Semantics増減・activateおよびpull-to-refreshを操作しても、選択と受理対象が変わらない
- 遷移前確認が次の描画フレームまで継続する場合にbusyが表示され、VoiceOver通知は1回だけである。route push受理または失敗案内後にbusyを解除し、routeから復帰した直後または分析画面に留まる失敗直後に再度タップできる
- 初期シーク要求前の初期化中に戻るとintentがabandonedになり、遅延完了後のシーク、通知および未処理例外が0件である
- 初期シーク要求後、シーク完了Futureの待機中に戻るとintentがconsumedのまま維持され、遅延完了後の追加シーク、通知および未処理例外が0件である
- 遷移前確認中に分析画面を破棄しても、遅延完了後の追加route、通知および未処理例外が0件である
- 動画初期化を意図的に遅延させた場合、準備中表示に対象工程名があり、未確定の0秒を成功状態として表示せず、再生・スキップ・Sliderが無効で、戻る操作だけは有効である
- pending中に別routeをpushし、route非currentを処理するpost-frame callbackより先に同一フレーム内で動画長取得不能またはcontroller初期化／runtime errorを完了させても、非current routeへエラーまたは状態を適用せず、戻った後に古いintentを再開しない
- すべての非同期処理が完了した安定retryable状態で動画ヘルプを開いて戻った場合は、明示的な再確認権を保持し、自動では再試行しない
- 候補snapshot作成後かつ初期シーク要求前に開始位置を変更すると、要求0回でintentがabandonedになる
- 候補snapshot作成後かつ初期シーク要求前に開始位置を消去または対象工程行を削除すると、要求0回でintentがabandonedになり、記録位置の削除を案内する
- retryable中に開始位置を変更した場合は、明示的に再確認しても旧intentを再開せず、要求0回でabandonedになる
- 直接遷移後かつ初期シーク要求前に症例を削除すると、要求0回でintentがabandonedになる。draft未初期化と初期化済みの両fixtureで、§8所定のnot-foundまたは削除bannerとデータ保護導線を確認する
- 初期シーク要求後に症例を削除すると、intentはconsumedのまま、追加要求0回で既存の削除bannerとdraft保護を表示する
- 初期シーク要求後に開始位置を変更すると、要求を置換せず追加要求0回で最新工程記録を表示する
- 初期シーク要求後に開始位置を消去または対象工程行を削除すると、intentはconsumedのまま、追加要求0回で記録位置の削除を案内する
- 初期シーク要求前に動画参照を変更すると、旧controllerへの要求0回でintentがabandonedになる
- resolverまたは最終fresh read中に動画参照A→C→Aを観測した場合、最終値が候補snapshotと一致しても要求0回でintentがabandonedになる。未来の `updatedAt` 等、timestampの大小だけでは復活させない
- 初期シーク要求後に動画参照を変更すると、intentはconsumedのまま、旧controllerの遅延完了を破棄し、追加要求0回で既存の動画回復UIを表示する
- 同じ動画参照の初期化失敗後、Provider再通知だけでは再開せず、明示的な再確認によってだけretryableからpendingへ戻る。その際は失敗したcontrollerを新controller生成前に論理的に切り離して旧世代を無効化し、listener解除後の次フレームで物理disposeを開始して、その完了・失敗を処理対象とする
- `availableLegacy` の移行成功時は旧参照の完了を破棄し、intentをpendingのまま管理参照へ結び直して初期シークを1回だけ要求する。移行失敗時は外部原本へ結び直し、同じく要求を1回だけとする
- `availableLegacy` の正規化中に旧参照A→第三参照C→A→正規化参照Bを観測した場合は、最終metadataがA→Bの対応を示してもintentを復活させず、要求0回とする。旧Aの遅延Provider通知と、正規化結果Bの通知順が逆転するだけの正常移行は1回だけ要求する
- 初期シーク後にProviderを再通知する
- 初期シーク後に画面を再buildする
- 初期シーク後にbackground／foregroundを行う

routeと初期シークは、受理した1件に対してそれぞれ最大1件とする。論理的に利用可能なcontrollerは同時に1件以下とし、明示的な再確認または動画変更による逐次再生成を許容する。listenerを安全に外すため、論理無効化済みの旧物理controllerがdispose開始まで最大1描画フレーム残ることは許容するが、再参照、UI反映またはシークに使用してはならない。古いFutureの完了が現在の画面状態を変更してはならない。

§7 R-5および§8の各異常系について、intentが `consumed`、`abandoned` または `retryable` のどの状態になるかを確認する。`consumed`／`abandoned` は通常のProvider再通知やlifecycle復帰で `pending` へ戻らず、`retryable` はユーザーの明示的な再確認によってだけ `pending` へ戻ることを確認する。

### 14.6 戻る操作と再取得

- clean状態では標準の戻る操作1回で分析画面へ戻る
- 同一内容が残る場合は表示工程、選択症例および戻る前のscroll offsetを±1 logical pixel以内で保持し、内容が短くなった場合だけ新しい有効範囲へクランプする
- 戻るたびに分析データを再取得する
- 工程時刻変更後はグラフと平均を更新する
- 対象点が消えた場合は最新有効点へフォールバックする
- 0件になった場合は空状態を表示する
- dirty状態では既存の保存・破棄・キャンセル確認を表示する
- 再取得失敗時は既存の分析エラーと再試行UIを表示し、再試行成功後に選択・scrollフォールバックを適用する
- VoiceOverの復帰先は、グラフが残る場合は同じadjustable control、0件の場合は当該工程の空状態見出しとする

### 14.7 アクセシビリティと表示環境

Semantics、操作、通知および代表レイアウトは自動テストし、実機支援技術と全表示環境の組合せは§19.3の手動受入matrixで受け入れる。

- グラフ全体が1つのadjustable Semantics nodeである
- VoiceOverのincrement／decrementでは症例選択だけが変わる
- VoiceOverのactivateで、選択中症例の対象工程を直接開く
- 総手術時間には直接ジャンプactionがない
- Semanticsのvalueに全件数中の位置、日付、左右眼、工程名および所要時間が含まれ、個別工程には直接ジャンプhintがあり、総手術時間にはそのhintがない
- busy、成功および失敗に、色以外の視覚表示またはテキストと適切なSemantics labelがある
- 成功と失敗を1回だけ適切に読み上げる
- 戻った際に同じグラフへフォーカス復帰できる
- `MediaQuery.disableAnimations == true` で本機能が追加する非必須モーションが停止する
- 自動テストでは文字倍率1.0／2.0、Light／Dark、320×568相当、モーション低減および動的リサイズの代表境界で操作喪失・overflowがない
- 手動受入matrixではiPhone／iPad実機、宣言済み全方向およびiPad Split Viewを上記の文字倍率・themeと組み合わせ、操作喪失・overflowがない

### 14.8 資源と回帰

- 自動テストでopen／backを20回連続実行し、各cycleのcleanup描画後にplatform controllerが0件であることを確認する。全cycleで同時に論理利用可能なcontrollerは最大1件とする
- 代表する初期化待ち、シーク待ちおよびdispose遅延・失敗fixtureでは、離脱時に旧世代を即時に論理無効化し、遅延callbackからUI、通知または追加シークへ反映しないことと、listener解除後の次描画フレームで物理disposeを開始して最終的にplatform controllerを残さないことを確認する
- legacy移行または明示的な再確認でcontrollerを結び直す場合は、旧世代の遅延完了が新controller、UIまたはシークを変更せず、逐次的な再生成中も同時に論理利用可能なcontrollerを1件以下に保つ。内部event順そのものではなく、世代分離、旧callback無効、旧player disposeおよび新playerだけが利用可能であることを観測して合否を判定する
- 初期シーク後の位置通知、再build、Provider再通知およびlifecycle復帰による追加の初期シーク要求が0件である
- 初期表示安定後に動画位置通知を10回発生させ、工程タブ、工程時間カード、自己評価および反省点入力を含む代表的な非動画subtreeのWidget identityとrebuild境界が維持されることを確認する。動画位置表示・操作部等の動画依存subtreeのbuildはこの制約に含めない
- 分析表示、指標変更、グラフ空白・前後症例・VoiceOver増減による選択だけでは、動画状態確認とcontroller生成がともに0件である
- 正常、フォールバック、範囲外、初期化失敗およびシーク失敗の前後で、工程時刻、評価、反省点、症例メモ、`videoPath`、`videoDisplayName` および `updatedAt` が同一であることをsnapshot比較する
- legacy移行成功時だけは、§12.2の動画関連metadata差分を許容して外部原本が残ることを確認する。移行失敗時は既存データが変わらない
- metadataを返さない動画解決互換APIは、通常managed参照とlegacy移行成功参照では最新DBと一致するfileを返し、legacy A→managed Bのcommit直後に別動画Cへ差し替わる競合、症例削除および最終DB再読込例外では旧fileを返さず `null` へfail-closedする
- 旧DBでは工程レビュー画面を開いた時だけ不足する空行が補完され、既存行は変わらない。遷移前フォールバックでは空行を作成しない
- 通常導線では直接ジャンプ用タブ選択・初期シークを発火しない。未完了工程あり／なしのfixtureで、既存のpost-frameタブ選択結果と既存の動画位置が変わらないことを確認する
- 既存の分析、症例詳細、工程レビュー、動画管理および未保存変更保護のテストが通る

## 16. 設計制約と実装時の参考

本節は観測可能な要件を置き換えない。実装方式を変更する場合も、§15の受け入れ基準を満たすこと。

### 16.1 遷移intent

工程レビュー画面には、`recordId` と対象工程の安定した識別子を渡す。開始位置は渡さず、遷移先で現在の `SurgicalStepReview` を再取得する。

### 16.2 工程行の取得

遷移可否判定では、行を生成しない `getStepReview` 相当の読み取りを用いる。1症例1工程の現在値を取得するため、「最新の開始時刻」という履歴が複数存在する前提を置かない。

本書の「最新」は、直接ジャンプ処理の開始後にrepository／serviceからfresh readした値を指す。非autoDisposeのFutureProvider等に残る既取得値を、再取得または明示的なinvalidateなしに最新値とみなさない。

工程レビュー画面では、候補snapshotに使う開始位置と、対象工程タブへ表示する工程記録を同じfresh readへ同期させる。動画だけ新しい位置へ移動し、工程カードには古い位置を表示する状態を作らない。この同期だけでdraftをdirtyにしない。

### 16.3 動画初期化とシーク

既存の動画状態解決、controller世代管理、動画参照一致判定および `VideoSeekCoordinator` 相当を再利用する。

低層のシーク範囲制限はクラッシュ防止として維持する一方、直接ジャンプの上位層では範囲を先に検証し、不正値をcontrollerへ渡さない。

同一ファイルパス・同一動画参照の初期化に失敗したcontrollerを、参照一致だけを理由に再利用しない。retryable状態からユーザーが明示的に再確認した場合は、失敗したcontrollerを新しいcontrollerの生成前に論理的に切り離して世代を更新する。widget listenerが外れる次フレームを要求して物理disposeを開始し、そのFutureの遅延・例外を未処理にせず、古いcallbackを無効化した上で初期化を再試行する。初期化失敗controllerのdispose完了だけを無期限に待って再試行を停止させない。通常のProvider再通知またはlifecycle復帰だけでは再生成しない。

### 16.4 画面遷移

分析画面を置換せず、同一Navigatorへpushする。pushが受理されて遷移先routeがactiveになった時点で分析画面のbusy処理を終了し、routeが戻った時点で分析データを再取得する。

## 17. 設計思想

本機能の中心は、多機能化ではなく次の一貫した体験である。

> 気になる個別工程の点をタップしたら、正しい症例の正しい工程を、安全にすぐ確認できる。

直接性だけを優先して、空白タップで意図せず遷移する、別症例・別工程を開く、不正位置を正常と見せる、または未保存データ保護を迂回することは許容しない。

「データを見る機能」と「手術を振り返る機能」をつなぎながら、既存の探索、詳細確認、編集、動画回復およびアクセシビリティを維持する。
